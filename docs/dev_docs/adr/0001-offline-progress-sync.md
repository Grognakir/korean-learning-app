# ADR-0001: Офлайн-запись прогресса SRS через event log (outbox)

Статус: принято
Дата: 2026-08-21

## Контекст

В MVP-плане (`0-mvp.md`) изначально было зафиксировано: офлайн — только чтение, оценка карточки (кнопки SRS) требует сети. Решение пересмотрено — офлайн-запись прогресса переносится в MVP, т.к. для языкового приложения это часть ценности (повторение в дороге, без связи), а не второстепенная фича.

Ограничения, влияющие на решение:

- Сессия хранится в httpOnly cookie через `@supabase/ssr` (осознанный выбор против XSS-кражи токена). Браузерный JS не имеет доступа к токену → офлайн-запись не может идти как прямой вызов `supabase-js` из клиента, только через собственный Next.js API route / server action, куда cookie прилетает автоматически при `fetch` на свой домен.
- Приложение — PWA, устанавливаемое на телефон; вероятна аудитория на iOS. Background Sync API в Safari/WebKit не поддерживается — нельзя полагаться на него как на единственный механизм синхронизации.
- Прогресс — накопительные данные, необратимые при потере (не кэш, который можно перезапросить). Мультиустройственный сценарий (телефон + компьютер) не основной, но реален.

## Рассмотренные варианты

1. **State-based запись.** Клиент офлайн сам считает итоговые `interval`/`due_at` и отправляет готовое состояние, когда появится сеть. Просто в реализации. Минусы: конфликт двух устройств решается грубым last-write-wins по таймстампу — один из результатов тренировки молча теряется; сам факт прохождения карточки нигде не фиксируется, только финальное состояние.
2. **Event log / outbox.** Клиент офлайн копит сырые события «оценил карточку X как `rating` в момент T», а не готовое состояние. Сервер — источник истины, пересчитывает состояние как свёртку (fold) событий той же функцией, что использует клиент для оптимистичного UI. Сложнее по объёму кода (нужна таблица событий, идемпотентность на сервере), но: мультиустройственный мёрдж — это просто объединение и сортировка событий по времени, потери данных нет, аудит/аналитика появляются бесплатно.
3. **Ничего не делать** — оставить офлайн только на чтение, как было решено раньше. Ноль дополнительной работы, но не закрывает сценарий «нет сети в дороге», который является частью ценностного предложения приложения.

## Решение

Вариант 2 — event log / outbox.

Главный аргумент: для накопительных, необратимых при потере данных корректность важнее простоты. Мультиустройственный сценарий хоть и не основной, но реален, и грубый last-write-wins там означает тихую потерю результатов тренировки — для приложения, где сам смысл — накапливать прогресс, это неприемлемая цена экономии кода.

Компоненты решения:

- **Общая чистая функция** `scheduleReview(state, rating) → nextState` — один модуль в кодовой базе, используется и клиентом (оптимистичный UI: следующая карточка сразу показывает актуальный `due_at`), и сервером (авторитетный пересчёт). Один источник правды для формулы SRS, расхождения клиент/сервер исключены самой структурой (общий модуль в монорепо Next.js).
- **IndexedDB outbox на клиенте**: `pending_reviews { id: uuid, item_id, rating, reviewed_at }`. Пишется при каждой оценке карточки вне зависимости от наличия сети.
- **Flush очереди** — обязательный универсальный механизм: слушатели `online` (window event) и `visibilitychange` (возврат приложения на передний план). Работает одинаково на всех платформах, включая iOS Safari.
- **Background Sync API** — опциональное ускорение там, где браузер поддерживает (Chrome/Android), не единственный механизм синхронизации.
- **Серверный роут** `/api/progress/review` (Route Handler): читает сессию из cookie через `@supabase/ssr`, валидирует payload Zod-схемой, проверяет идемпотентность по `id` события (повторная отправка после обрыва флаша не должна задвоить результат), применяет событие.
- **Таблица `review_events`** (append-only) — источник истины: `id` (uuid, уникальный — основа идемпотентности), `user_id`, `item_id`, `rating`, `reviewed_at`. RLS аналогично `progress`: `USING`/`WITH CHECK (auth.uid() = user_id)`.
- **`progress`** остаётся, но становится денормализованной проекцией текущего состояния SRS — пересчитывается из `review_events`, используется для быстрого чтения дэшборда/очереди повторения без пересчёта истории на каждый запрос.

## Последствия

Чем платим:

- Дополнительная таблица `review_events` + RLS-политики для неё.
- Клиентский IndexedDB-слой (outbox) и логика flush с ретраями/backoff.
- Дополнительное тестовое покрытие: «оценил офлайн → вернулась сеть → применилось ровно один раз», «два устройства офлайн одновременно → корректный мёрдж после синхронизации обоих».
- Явный дополнительный шаг в roadmap реализации MVP (был неявно предполагаемым «попозже», теперь — часть MVP-объёма).

Что становится проще:

- Мультиустройственная синхронизация в будущем не потребует переделки модели данных — событийный лог уже это закладывает.
- Аудит и аналитика («сколько раз и когда пользователь занимался») получаются бесплатно, без отдельного трекинга.

Пересмотреть решение, если: реальные метрики покажут, что офлайн-использование почти не встречается (тогда можно упростить до state-based); либо объём событий на пользователя вырастет настолько, что `review_events` потребует партиционирования/архивации — не ожидается на масштабе пет-проекта.

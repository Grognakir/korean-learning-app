# 0. MVP — план реализации

## Обзор

PWA-приложение для изучения корейского языка. Устанавливается на телефон как иконка ("Добавить на экран"), работает офлайн для уже загруженного контента, не требует публикации в App Store/Google Play.

Проект начинается с чистого листа. Референсы `korean_flashcards` и `korean_learning` использовались только как источник идей (проверенный набор пакетов, дизайн-язык) — код и архитектура не копируются.

## Модель доступа: гость и авторизованный пользователь

**Принцип:** бо́льшая часть функционала доступна сразу, без регистрации. Логин обязателен только там, где приложению нужно **что-то сохранить за конкретным пользователем** — в первую очередь запись прогресса (SRS), и, по мере появления, часть материала (какая именно — решается отдельно по каждому разделу при его реализации, единого заранее зафиксированного списка «закрытых» разделов нет).

**Почему:** это снижает барьер входа — попробовать приложение можно сразу при открытии, без создания аккаунта; логин становится осознанным шагом «хочу, чтобы результат сохранился», а не преградой перед первым касанием продукта.

**Как это реализовано технически:** нет единой «стены логина» на уровне middleware для контентных роутов. Каждый роут сам решает, что показать — компонент читает `supabase.auth.getUser()` и рендерит разное содержимое для гостя и авторизованного (пример — `/`: гость видит лендинг с призывом войти/зарегистрироваться, авторизованный сразу видит дэшборд с прогрессом; редиректа между этими состояниями нет, это две ветки одного компонента). `PROTECTED_PREFIXES` в `lib/supabase/middleware.ts` защищает только те роуты, которые **физически не могут работать без пользователя** — например, будущий `/api/progress/review`: без `user_id` там нечего обрабатывать. Список этого поля растёт по мере появления таких роутов, а не привязан к «приватности» контента как такового.

**Гостевой прогресс не сохраняется.** `review_events`/`progress` жёстко привязаны к `user_id` (`NOT NULL`, FK на `auth.users`) — если гость без аккаунта пройдёт тренировку, результат нигде не запишется (ни в БД, ни в `localStorage`) на этом этапе MVP. UI тренировки для гостя должен явно это показывать (например, баннер «войдите, чтобы сохранить прогресс»), а не создавать иллюзию сохранённого результата. «Гостевой прогресс с последующей миграцией в аккаунт при регистрации» — отдельное расширение, не в текущем скоупе.

## Технологический стек

| IndexedDB (нативный API или `idb`-обёртка) | Локальная очередь офлайн-событий | Outbox для событий прогресса, накопленных без сети (см. раздел «Офлайн-режим») |

| Playwright | E2E-тесты | Критичные флоу: регистрация → подтверждение → логин → доступ к приватной странице |
| pnpm | Пакетный менеджер | Быстрее и экономнее npm по дисковому пространству |
| Vercel | Хостинг/деплой | Нативная интеграция с Next.js, автоматический HTTPS, деплой по пушу в git |

## Безопасность и авторизация

Это ядро документа — авторизация, регистрация и прогресс пользователя должны быть защищены на каждом уровне.

1. **Аутентификация — Supabase Auth**
   - Регистрация по email + паролю, обязательное подтверждение email перед первым входом
   - Пароль — минимальные требования к длине/сложности задаются в настройках Supabase Auth
   - OAuth-провайдеры (Google и т.п.) не входят в MVP, но Supabase Auth их поддерживает "из коробки" — можно добавить позже без смены архитектуры

2. **Хранение сессии**
   - Сессия живёт в httpOnly cookie через `@supabase/ssr`, недоступна из клиентского JS
   - Next.js middleware обновляет сессию на каждом запросе и защищает те немногие роуты, которые не могут работать без пользователя (см. «Модель доступа: гость и авторизованный пользователь») — это не общая «стена логина» для контентных страниц
   - Это же ограничение определяет архитектуру офлайн-записи прогресса: раз токен недоступен из JS, клиент не может писать в Supabase напрямую даже когда сеть появляется в service worker — запись идёт только через собственный API-роут, куда cookie прилетает автоматически (см. «Офлайн-режим»)

3. **Row Level Security (RLS) в Postgres**
   - Включена на всех таблицах с пользовательскими данными
   - Политики задаются отдельно для каждой операции: `USING (auth.uid() = user_id)` для `SELECT`/`UPDATE`/`DELETE` и обязательно `WITH CHECK (auth.uid() = user_id)` для `INSERT`/`UPDATE` — без `WITH CHECK` пользователь теоретически может вставить или переписать строку с чужим `user_id`
   - RLS — это защита на уровне БД, а не только приложения: даже при ошибке в серверном коде утечки чужих данных через прямой запрос к Supabase не будет

4. **Разделение ключей Supabase**
   - `anon` key — единственный ключ, который попадает в клиентский бандл; его возможности ограничены RLS-политиками
   - `service_role` key — только в серверном окружении (`.env`, никогда не в NEXT_PUBLIC_* переменных), используется исключительно там, где нужно обойти RLS (например, административные скрипты)

5. **Валидация данных**
   - Zod-схемы для форм регистрации/логина и для API/server actions
   - Клиентская валидация — для UX (мгновенная обратная связь), серверная — обязательна и не доверяет клиенту: любые данные, пришедшие от клиента, валидируются заново на сервере

6. **Прочее**
   - Ограничение количества попыток входа/регистрации — базово обеспечивается Supabase Auth, при необходимости дополняется на уровне middleware
   - HTTPS обеспечивается автоматически на Vercel
   - Секреты и `.env.local` не коммитятся в git (добавить в `.gitignore` сразу при инициализации проекта)

## Модель данных (первая версия)

- **`profiles`** — `id` (uuid, ссылка на `auth.users`), `username`, `created_at`, `font_latin` и `font_kr` (nullable, дефолт `null` → системный/базовый шрифт; выбор пользователя из набора в `2-design-system.md`). Для гостя без аккаунта — то же самое, но в `localStorage`
- **`review_events`** — источник истины (append-only, события не изменяются и не удаляются): `id` (uuid, генерируется клиентом — основа идемпотентности при повторной отправке), `user_id`, `item_id`, `rating`, `reviewed_at`. Каждая оценка карточки — отдельная запись, а не перезапись состояния
- **`progress`** — производная проекция текущего состояния SRS для быстрого чтения (дэшборд, очередь повторения): `user_id`, `item_id`, `item_type` (например `flashcard`), `interval`, `ease_factor`, `due_at`, `last_reviewed_at`. Пересчитывается сервером как свёртка (fold) событий из `review_events` той же функцией `scheduleReview`, что использует клиент для оптимистичного UI — расхождений клиент/сервер не возникает, т.к. это один и тот же модуль кода
- **`item_id` — стабильный строковый slug, а не индекс массива.** Присваивается карточке один раз при создании и не меняется. Если завязать `item_id` на позицию в JSON-массиве, любая правка порядка контента (вставка карточки в середину, пересортировка) молча "переносит" прогресс пользователя на другую карточку — дешёво зафиксировать это правило сейчас, дорого чинить миграцией данных позже
- Контент карточек/уроков на этапе MVP — статический seed-файл в репозитории (JSON), без отдельной таблицы прав доступа, т.к. не редактируется пользователем
- RLS на `review_events` — аналогично `progress`: `USING`/`WITH CHECK (auth.uid() = user_id)`

## PWA-обвязка

- `manifest.json` — имя приложения, иконки, `theme_color`, `display: standalone`
- Иконки 192×192 и 512×512
- Service worker через Serwist — кэш статических ассетов, офлайн-фоллбек страница, кэширование данных для уже пройденных карточек

## Офлайн-режим и запись прогресса

Полноценная офлайн-запись прогресса входит в MVP. Подробное обоснование выбора и рассмотренные альтернативы — в **ADR-0001** (`docs/dev_docs/adr/0001-offline-progress-sync.md`). Здесь — рабочая схема:

- Оценка карточки (кнопки SRS-грейдинга) работает офлайн без ограничений. Событие `{ id, item_id, rating, reviewed_at }` пишется в локальную очередь (**outbox**) в IndexedDB, вне зависимости от наличия сети. UI обновляется оптимистично той же функцией `scheduleReview`, что использует сервер, — следующая карточка сразу показывает актуальный `due_at`.
- **Синхронизация** запускается по событиям `online` (появилась сеть) и `visibilitychange` (приложение вернулось на передний план) — это базовый механизм, работающий на всех платформах, включая iOS Safari. Background Sync API используется как необязательное ускорение там, где браузер его поддерживает (Chrome/Android); полагаться только на него нельзя — в Safari/WebKit он не реализован.
- Флаш отправляет накопленные события по одному на `/api/progress/review`. Сессия передаётся автоматически (httpOnly cookie на same-origin запросе), отдельная передача токена не нужна.
- Сервер проверяет `id` события на повторную обработку (идемпотентность — на случай, если флаш прервался и повторился), валидирует Zod-схемой, применяет к `review_events`, пересчитывает `progress`.
- Мультиустройственный конфликт (два устройства офлайн одновременно) решается естественным образом: события с обоих устройств просто сливаются в общую историю `review_events` и упорядочиваются по времени — потери данных нет, в отличие от записи готового состояния с last-write-wins.

## Известные компромиссы

- **Supabase — единая точка отказа.** Auth и БД живут в одном внешнем сервисе; при его недоступности недоступно всё приложение. Для MVP это осознанный трейдофф — свой auth + своя БД избыточны для проекта такого масштаба.
- **Пауза free-tier проекта при неактивности.** Supabase на бесплатном тарифе приостанавливает проект после длительного простоя — первый запрос после паузы отработает с задержкой на "холодный старт". Стоит иметь в виду для проекта, которым пользуются не каждый день, и не путать с багом.
- **Офлайн-синхронизация добавляет объём работы.** Event log/outbox (ADR-0001) выбран сознательно ради корректности при потере сети и мультиустройственных конфликтах — цена: отдельная таблица `review_events`, клиентский IndexedDB-слой, идемпотентность на сервере, дополнительные тестовые сценарии. Решение того стоит, т.к. офлайн-повторение — часть ценности приложения, а не второстепенная функция.

## Скоуп MVP

1. Регистрация / логин / логаут (email + пароль)
2. Главный экран — доступен без логина (лендинг), авторизованному показывает дэшборд с прогрессом (см. «Модель доступа»)
3. Один обучающий модуль — флэшкарты с простым интервальным повторением (SRS); прохождение доступно без логина, запись прогресса — только авторизованному
4. PWA: устанавливаемость на экран телефона + офлайн-доступ к уже загруженным карточкам, включая прохождение и запись прогресса без сети (синхронизация при восстановлении сети — см. «Офлайн-режим» и ADR-0001)
5. Переключение шрифта отображения — рус/eng и корейский, включая рукописный вариант для корейского (набор шрифтов и обоснование — см. `2-design-system.md`)

## Вне скоупа MVP

- Модули грамматики, хангыля/произношения, подготовки к TOPIK — следующие этапы после обкатки основы
- OAuth-вход (Google и т.п.)
- Push-уведомления

## Roadmap шагов реализации

1. Инициализация Next.js + TypeScript + pnpm + ESLint/Prettier
2. Supabase локально через CLI (`supabase init` + `supabase start`) для разработки и миграций; облачный проект (free tier) создаётся и линкуется позже, одним разом, когда схема стабилизируется — см. `dev_steps/1-database-and-auth-setup.md`
3. Схема БД (`profiles`, `review_events`, `progress`) и RLS-политики в виде миграций (`supabase/migrations`)
4. Auth-флоу: регистрация, подтверждение email, логин, логаут, middleware обновления сессии (защита конкретных роутов добавляется по мере появления тех, что не могут работать без пользователя — см. «Модель доступа»)
5. Модель прогресса и первый обучающий модуль (флэшкарты): функция `scheduleReview`, серверный роут `/api/progress/review`, онлайн-запись
6. Офлайн-запись прогресса: IndexedDB outbox, оптимистичный UI, флаш по `online`/`visibilitychange`, идемпотентность на сервере (ADR-0001)
7. Переключение шрифта отображения: подключение шрифтов (`next/font/google` для большинства, self-host `@fontsource/pretendard` для Pretendard), UI-переключатель, сохранение выбора в `profiles`/`localStorage` (см. `2-design-system.md`)
8. PWA-обвязка: `manifest.json` + Serwist service worker
9. Тестовое покрытие и CI: Vitest для логики SRS и валидации, Playwright для auth-флоу и сценариев офлайн-записи/синхронизации прогресса, пайплайн GitHub Actions (см. `1-cicd-and-testing.md`)
10. Деплой на Vercel (см. `1-cicd-and-testing.md` — интеграция Vercel и решение по миграциям Supabase)

# 1. CI/CD и стратегия тестирования

## Принцип

Время ожидания тестов растёт не с числом тестов вообще, а с числом *медленных* тестов — реальный браузер, реальная сеть, реальный бэкенд. Поэтому основная защита от долгого ожидания — не тюнинг CI, а дисциплина тестовой пирамиды: всё, что можно проверить без браузера (расчёт SRS, Zod-валидация, идемпотентность на уровне функции), проверяется Vitest'ом за миллисекунды; Playwright E2E остаётся тонким слоем только для критичных сквозных путей. Технические приёмы ниже ускоряют именно E2E-часть — они не заменяют дисциплину, а работают поверх неё.

Критичные пути, которые оправдывают E2E (не больше, если не появится веская причина):
- Регистрация → подтверждение email → логин → доступ к приватной странице
- Запись прогресса онлайн
- Запись прогресса офлайн + синхронизация при восстановлении сети (ADR-0001)

## Локальная разработка (dev loop)

- **Vitest** — watch-режим с фильтром по изменённым файлам (`vitest --changed` или обычный watch), не весь набор на каждое сохранение.
- **Playwright** — во время разработки гонять вручную только нужный файл/тег (`playwright test path/to/file`). Полный прогон E2E — перед пушем/PR, не как часть цикла редактирования.

## CI: стадии пайплайна (GitHub Actions)

| Стадия | Триггер | Что выполняется | Ожидаемое время |
|---|---|---|---|
| Быстрый гейт | push в любую ветку, каждый коммит в PR | ESLint + typecheck (`tsc --noEmit`) + Vitest (полный набор) | секунды — до ~1 мин, растёт медленно даже при росте unit-тестов |
| E2E-гейт | PR, перед мержем в `main` | Playwright, шардированный на несколько параллельных джобов, против локального Supabase | единицы минут; растёт кратно медленнее числа тестов благодаря шардированию |
| Деплой | Vercel native GitHub-интеграция: preview на каждый PR, prod на merge в `main` | Сборка и деплой Next.js | вне GitHub Actions, отдельный процесс |

Быстрый гейт — обязательный чек на каждый коммит, должен оставаться быстрым всегда: если lint/typecheck/unit начнут занимать больше минуты, это сигнал разбираться (типичная причина — типизация тянет слишком много, а не сами тесты). E2E-гейт — обязательный чек перед мержем, но не гонится на каждый промежуточный коммит в фича-ветке.

## Приёмы ускорения E2E

1. **Playwright против локального Supabase, не облачного.** `supabase start` (Supabase CLI) поднимает Postgres + Auth в Docker прямо в CI-раннере. Убирает сетевую задержку до внешнего сервиса — обычно она доминирующая часть времени e2e с реальным бэкендом — и не тратит лимиты free tier облачного проекта на каждом прогоне.
2. **Переиспользование сессии между тестами.** Одна авторизация в Playwright setup-проекте, состояние сохраняется через `storageState`; остальные тесты стартуют уже залогиненными. Не гонять полный UI-флоу регистрации в каждом тесте, которому на самом деле нужен только залогиненный дэшборд.
3. **Шардирование с самого начала**, даже при малом числе тестов. Матрица на 2–4 параллельных джоба в GitHub Actions (`--shard=1/4`, `2/4` и т.д.). Ничего не стоит настроить сегодня при 5 тестах, но продолжает работать без переделки при 50 — если отложить, придётся возвращаться к уже отлаженному пайплайну и перекраивать его под нагрузкой боли, а не заранее.
4. **Кэширование окружения.** pnpm store, `.next/cache`, Playwright-браузеры — через `actions/cache`. Экономит время установки/сборки, а не самих тестов, но на маленьком проекте установка часто дороже прогона, особенно на старте.

## Миграции Supabase — сознательно ручной шаг на старте

На данном этапе: `supabase db push` выполняется вручную перед мержем PR, который меняет схему. Автоматизация (отдельный CI-шаг на merge в `main`, применяющий миграции к прод-проекту Supabase перед/после деплоя Vercel) — осознанно отложена, а не забыта. Пересмотреть, когда: ручной шаг хотя бы раз забудут выполнить и код с прод-схемой разъедутся, либо когда появится смысл в отдельном staging-проекте Supabase для end-to-end проверки миграций перед продом.

## Что меняется по мере роста набора тестов

Не вводить сейчас — переусложнение на пустом месте при текущем объёме, но иметь в виду:

- **PR-гейт остаётся smoke-подмножеством** критичных путей, даже когда E2E-сценариев станет много.
- **Широкий regression-набор** (граничные случаи, менее критичные флоу) — выносится в отдельный nightly/cron-прогон, а не в каждый PR.
- Сигнал к пересмотру — когда E2E-гейт на PR начинает превышать ~3–5 минут даже с шардированием: либо добавлять шарды, либо выносить часть тестов в nightly.
